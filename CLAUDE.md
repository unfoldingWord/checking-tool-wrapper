# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`checking-tool-wrapper` is a shared npm package used by translationCore's checking tools (`translationWords`, `translationNotes`). It is not a standalone app — it's consumed by a tCore tool's own `index.js`, which wires up `Api`, `Container`, and `reducers` from this package via `tc-tool`'s `connectTool`. See `README.md` for the exact integration snippet.

`src/index.js` is the public entry point and only exports: `Api`, `Container`, `reducers`, `getQuoteAsString`, `getAlignedTextFromBible`.

## Commands

- `npm test` — runs `eslint ./src` then `jest`. This is what CI and `prepublishOnly` run; both lint and tests must pass.
- `npm run lint` / `npm run lint:fix` — eslint only, `--fix` variant available as `npm run fix`.
- `npx jest __tests__/verseHelpers.test.js` — run a single test file.
- `npx jest -t "name of test"` — run tests matching a name.
- `npm run build` — babel-compiles `src` to `lib` (production `NODE_ENV`); `lib` is what gets published (see `files` in `package.json`). Don't hand-edit `lib`.
- `npm run test:llm` — runs `__tests__/llmModelSuitability.test.js`, which checks whether a model on a live OpenAI-compatible server (e.g. LM Studio) gives good AI suggestions for the cases in `__tests__/__fixtures__/llmEval/cases.json` (hand-written) and `realCases.json` (from translators' aligned projects). Requests go through `getBestSelections`, as the app sends them. Its live tests are skipped unless `LLM_EVAL_MODEL` is set, so `npm test` makes no network call; its always-running tests check the case files and that the algorithm path still gets the recorded number of cases right (`ALGORITHM_TOP1`). Settings and pass/fail thresholds are `LLM_EVAL_*` environment variables, listed in the test file's header.
- `npm run build:llm-eval-cases` — rebuilds `__tests__/__fixtures__/llmEval/realCases.json` from the aligned projects in `~/translationCore/projects` (see the header of `__tests__/buildLlmEvalRealCases.test.js`; skipped in `npm test`). After rebuilding, update `ALGORITHM_TOP1`.
- `npm run run:llm-training-data` — runs the files in `llmTrainingData` through `getBestSelections` and saves results and summaries in `llmTrainingData/results` (header of `__tests__/runLlmTrainingData.test.js`). Without `LLM_TRAINING_URL` it uses the algorithm; with `LLM_TRAINING_URL` and `LLM_TRAINING_MODEL` it asks the AI through `installNodeAiApis` (jest has no `fetch`), and when the algorithm results for a file exist it compares the two by the algorithm's confidence band, scoring the AI with the app's fallback to the algorithm, and prints the top-1 at each possible `ALGORITHM_CERTAIN_CONFIDENCE` (saved as `results/<model>.byAlgorithmConfidence.json`). Run the algorithm first.
- `npm run check:llm-training-data` — finds the cases in `llmTrainingData/*.json` that may not help train the AI (e.g. no expected word in the history, exactly or as another form by `wordSimilarity`, or an answer unusually long for its language: over that language's 99th percentile from `getAnswerLengthLimits` and over the longest history rendering + 2 words; languages space words differently, so there is no fixed word limit) and saves them, grouped by file, in `llmTrainingData/results/unhelpfulTrainingCases.json`. The reasons are `UNHELPFUL_REASONS` in `__tests__/helpers/suggestionsHelpers.js`; the unit tests in `__tests__/findUnhelpfulTrainingCases.test.js` run in `npm test`, the scan does not.
- `scripts/rebuild-llm-training-data.sh [-n] [-c] [-a] [-f]` — rebuilds every file in `llmTrainingData` from the translationCore projects with `__tests__/buildLlmTrainingData.test.js` (`-n` dry run, `-c`/`-a` refresh the unhelpful-case and algorithm results). A project's translationWords checks are for the GL last selected in translationCore, so files for another GL are skipped unless `-f`; the builder refuses them too unless `LLM_TRAINING_ALLOW_GL_MISMATCH=1`. To build a file for another GL, open the project in translationCore with that GL selected for translationWords first. The GL phrases come from the first GL bible (in `bibleIdSort` order) whose book is aligned, as the app does for a check's GL phrase; `LLM_TRAINING_GL_BIBLE` names one instead. Check new files' GL phrases are in the GL's language: Arabic `arst` v4.9_BSOJ has English text aligned in most books (Arabic only in a few, e.g. Titus, 1 Timothy), so the Arabic-GL files use `avd`. The history in the case files is counted as the app counts it: GL phrases and renderings lowercased with `getSelectionHistoryKey` (the builder passes the target language to `getSelectionsForBook`); files built before 2026-11-26 were converted in place with `LLM_TRAINING_LOWERCASE_HISTORY=1` (`toAppSelectionHistory`), which also converts the evaluation sets in `llmTrainingData/promptEval`. `plans/fine-tune-qwen3.md` holds the fine-tuning plan that uses this data.
- `npm run calibrate:algorithm` — measures the algorithm's confidences against the training data (`plans/algorithm-confidence.md`): runs every case in `llmTrainingData/*.json` through `getBestSelections` with `explainAlgorithm`, splits the projects into tune and held-out test, and prints top-1, calibration error, Brier score, AUC, accuracy by confidence band and at 100, and per-project accuracy; writes `llmTrainingData/results/algorithmCalibration.jsonl` (one row per option, with its features) and `.report.txt`, and counts answers that differ from the saved algorithm results. Settings are `LLM_ALGO_*` variables in the header of `__tests__/calibrateAlgorithm.test.js` (`LLM_ALGO_OPTIONS` passes algorithm options, e.g. `fuzzyPassBelow`); its helper unit tests run in `npm test`. `__tests__/calibrateAiConfidence.test.js` (with `LLM_ALGO_AI_MODEL`) rescores saved AI answers with `scoreSelectionsFromHistory`, which the app does not use (AI confidences stay as the AI gives them).
- `npm run add:ol-words` / `npm run measure:ol-history` — Step 1 of `plans/original-language-history.md` (original-language keys for the history). `add:ol-words` adds `olWords` (the quote's Greek or Hebrew words with lemma, Strong's number and morphology, from the newest unfoldingWord `ugnt`/`uhb` in `~/translationCore/resources`) to every case file in `llmTrainingData` and `llmTrainingData/promptEval`; `buildLlmTrainingData.test.js` writes it too. `measure:ol-history` builds each case's lemma- and form-keyed histories from the earlier cases of its group (`buildOlHistories` in `__tests__/helpers/olHistoryHelpers.js`) and writes `llmTrainingData/results/olHistoryMeasure.txt`/`.json`. `npm run measure:ol-cross-book` (Step 4; `LLM_OL_CROSS_ALGO=1` also runs the algorithm) measures OL history from a project's other books, which the GL bible cannot always key (header of `__tests__/olCrossBook.test.js`). The lookup helpers are in `src/utils/originalLanguageUtils.js`.
- `npm run build:prompt-eval-cases` — builds the seeded evaluation sets of `plans/improve-single-prompt.md` in `llmTrainingData/promptEval/` (`dev`, `dev-nohist`, `test`, `test-nohist` case files, `meta/manifest.json`): DEV is 1,500 cases the app sends to the AI from projects outside the fine-tune's test files; TEST is every case of those test files. Run the algorithm on them afterwards (`LLM_TRAINING_DATA_DIR=llmTrainingData/promptEval npm run run:llm-training-data`) for `scripts/compare-prompt-variants.js`.
- `npm run build:finetune-data` — builds the fine-tuning data of `plans/fine-tune-qwen3.md` (Steps 2-3) in `llmTrainingData/finetune/` (git-ignored): `train.jsonl`, `valid.jsonl` and `test.jsonl` in the `messages` format `mlx_lm.lora` reads, matching `*.meta.jsonl` and `manifest.json` (counts, drops, round-trip failures, cases to hand-check). Each example is the exact prompt the app sends (`buildTranslationOptionsPrompt` + `applyThinkingDirective`), split by target project, filtered with the algorithm results and `findUnhelpfulTrainingCases`; run `npm run run:llm-training-data` (algorithm) first. Settings are `LLM_FINETUNE_*` variables in the header of `__tests__/buildFineTuneData.test.js`, whose parity test (in `npm test`) fails if the app's prompt changes without the exporter. `LLM_FINETUNE_NO_HISTORY_SHARE` (default 0; the current models use 0.1) adds that share of train and valid examples again with no history; `LLM_FINETUNE_PROMPT_VARIANT` builds the examples with a prompt variant of `promptVariants.js` (parity-tested for `X4b` and `N34`; neither beat the app's prompt once trained, `plans/improve-single-prompt.md` Step 7).
- `llmTraining/` — the Python side of that fine-tune (Apple MLX, `mlx-lm`; its own `.venv`, git-ignored, as are `outputs/`, `.venv-gguf/` and `.llama.cpp/`). `llmTraining/README.md` has setup, training, fusing and the GGUF conversion for Windows and Linux. `check_data.py` checks the exported data renders like the app's prompt (run it after `build:finetune-data`); the `*.yaml` files are the training runs of the plans; the current ones are `lora-r16-r0v2.yaml` (Qwen3-1.7B), `lora-r16-r0v2-0.6b.yaml` and `lora-r16-r0v2-4b.yaml` (Qwen3-4B-Instruct-2507, which has no thinking mode, so its trained part has no empty think block), all LoRA r16 on the data built with `LLM_FINETUNE_INCLUDE=noRelatedWordInHistory LLM_FINETUNE_NO_HISTORY_SHARE=0.1 LLM_FINETUNE_OUT_DIR=llmTrainingData/finetune-r0v2` (the first release, `d3`, used `lora-r16-d3*.yaml`); `train_full.py` runs a full fine-tune in float32; `handcheck.py` makes a local page for hand-checking a sample of a case group. On the held-out TEST files (835 checks; `llmTrainingData/promptEval/test*.json`), with history / with none: 1.7B 72.3% / 65.0%, 0.6B 67.7% / 49.7%, 4B 73.7% / 69.2% at twice the 1.7B's time, against d3 1.7B 67.4% / 54.3% and stock `qwen3-4b-2507` 58.6% / 36.0% (`plans/improve-single-prompt.md`, Step 8A). Release builds (`llmTraining/make_release.sh`, which takes the run name from `RUN`, default `r0v2`; cards in `llmTraining/model-card*/`): 1.7B MLX 5-bit for Mac and GGUF Q5_K_M for Windows and Linux; 0.6B MLX 6-bit and GGUF Q6_K for computers that cannot run the 1.7B; 4B MLX 5-bit and GGUF Q5_K_M as a large option. The 4B files are over GitHub's 2 GiB limit per release file, so the script leaves them out of `github-release/` (publish them on Hugging Face). Large models are saved in shards by `mlx_lm.fuse`: link every `*.safetensors` when staging the GGUF conversion. Score GGUF builds through plain llama.cpp (`llama-server`): LM Studio's llama.cpp engine on the Mac gives lower, different answers for Qwen3-1.7B (stock too). The fine-tune is trained on single requests only: it must be used with one request per query (`llmGrouping` 1, the default), since with batches it drops the `### REQUEST n` markers and most answers come back empty. Changing the system prompts or `formatPreviousTranslations` means rebuilding the data and retraining.

Scripts in `scripts/` wrap that suite. Each prints its usage with `-h`. They write logs and JSON results to `llm-eval-results/`, which is git-ignored.
- `scripts/test-llm.sh [-u URL] [-r RUNS] [-g GROUPING] [-t TEMP] [-k TOKEN] [-o DIR] model ...` — runs the suite once per model and prints each report plus a pass/fail summary. `-l` lists the server's models. Defaults: `http://localhost:1234`, falling back to `$LLM_EVAL_FALLBACK_URL` or `http://192.168.142.56:1234` when it does not answer and no `-u` was given; 2 runs; 4 requests per batched query; temperature 0.1 (the app's default). The reference models are `qwen/qwen3-1.7b` and `qwen/qwen3-4b-2507`; compare changes with `-r 3`. Exits 1 when any model fails a bar and 2 for a usage or server error.
- `scripts/compare-llm-runs.js [-c] [DIR [STAMP]]` — shows the models from one `test-llm.sh` run side by side (the latest run in `llm-eval-results/` by default). `-c` adds top-1 per case. Its "failed bars" row leaves out the request-error, thinking-off and batch-marker tests, so check the `.log` for those.
- Prompt experiments for single requests (`plans/improve-single-prompt.md`): variants are builders in `__tests__/helpers/promptVariants.js` (`baseline` is the app's prompt, checked byte for byte in `__tests__/promptVariants.test.js`; `beforeN3` is the app's prompt before the no-history prompt was added, which the variants measured before 2026-11-25 build on), selected with `LLM_PROMPT_VARIANT` in `run:llm-training-data` (result files get `_prompt-<id>`) and in the suitability suite. They reach the app's code path through `setSinglePromptOverrideForEval` in `checkingSuggestionsUtils.js` (eval only; the app never calls it). `scripts/compare-prompt-variants.js CASES A.results.json B.results.json` compares two runs case by case, with the app's fallback to the algorithm and an exact McNemar p, then sorts the wrong top answers by kind (too short, too long, wrong occurrence, partial, other, no answer) and splits top-1 by GL phrase length (`plans/prompt-span-experiments.md`). `queryAiAPI` also takes `options.messages` (a list of chat messages, e.g. examples as earlier turns), which goes through `window.AiAPIs` only when translationCore declares `features.messages`.
- `scripts/test-llm-temperatures.sh [test-llm.sh options] model ...` — runs `test-llm.sh` at each temperature in `LLM_EVAL_TEMPERATURES` (default 0.1 to 0.8) and prints a comparison table.

Tests live in `__tests__/` (not colocated with `src/`), with fixtures in `__tests__/__fixtures__/` and snapshots in `__tests__/__snapshots__/`. Enzyme (React 16 adapter) is configured in `jest.setup.js`. `fs-extra` is mocked globally via `__mocks__/fs-extra.js`.

## Architecture

### Data flow: tCore → this package

The host app (translationCore) passes down a large `tc` prop (see `getTcState`/`getContextId`/`getBibles` etc. in `src/selectors/index.js`) containing the current project's target book, resources (bibles, translationHelps, lexicons), project manifest, and settings. Nearly everything this package does is either:
1. reading from that `tc` state plus its own Redux slice (`state.tool.*`, combined in `src/state/reducers/index.js`: contextId, groupsIndex, groupsData, groupMenu, comments, selections, bookmarks, verseEdit, invalidated), or
2. reading/writing project files on disk directly via `fs-extra`/`path-extra` (check data, selections, group data JSON under `.apps/translationCore/...` in the project folder — see `src/common/constants.js` for the path constants).

`src/Container.js` is the top-level React component (function component using hooks) that lays out the checking UI: `ScripturePaneWrapper`, `VerseCheckWrapper`, `TranslationHelpsWrapper`, `CheckInfoCardWrapper`, `GroupMenuContainer`, wrapped in `TcuiThemeProvider`.

`Api.js` (`class Api extends ToolApi` from `tc-tool`) is the tool's lifecycle/API surface — validating verse alignments/selections when the book changes, loading verse/book selections and check data, and reacting to changes in other tools (e.g. word alignment invalidating selections).

### Helpers (`src/helpers/`)

Most business logic lives here as plain functions, organized by concern rather than by component — e.g. `groupDataHelpers`, `selectionHelpers`, `checkDataHelpers`, `verseEditHelpers`, `validationHelpers`, `gatewayLanguageHelpers`, `resourcesHelpers`, `contextIdHelpers`. When changing behavior, look for the relevant helper module before touching components/containers.

`fileHelpers.js` has low-level JSON/text/folder-tree read helpers plus version-folder resolution (`v9` vs `v10`-style comparisons) used when picking the most recent gateway-language bible resource.

### Auto-select suggestions (`src/utils/checkingSuggestionsUtils.js`)

Note this lives in `src/utils/`, not `src/helpers/`. It implements "auto-select" translationWords suggestions — matching a gateway-language (GL) phrase (`alignedGLText`) to word(s) in the target-language verse. Its tests are in `__tests__/checkingSuggestionsUtils.test.js` (algorithm path), `__tests__/checkingSuggestionsUtilsLlm.test.js` (AI parsing and batching, network mocked) and `__tests__/LlmRequestQueue.test.js`. To measure AI suggestion quality against a live model, use `__tests__/llmModelSuitability.test.js` and the `scripts/` described under Commands. `plans/improve-llm-suggestions.md` holds the measured results and the improvement plan.

Flow: `Container.js` → `LlmRequestQueue` (in its own module, `src/utils/LlmRequestQueue.js`, alongside the `RequestQueue` it wraps; caches results by key, see `alreadyHaveSuggestionsForKey`; supports pause/resume via `requestPause`) → `getBestSelections(jobs)` in `checkingSuggestionsUtils.js`, which picks one of two paths:
- No `llmQueryUrl` → `getBestTWordSelectionWithConfidenceAlgorithm(wordList, targetLangCode, glPhrase, glLangCode, previousTranslationData)` for each job. This path is deterministic and makes no network call. The history holds one translationWords group, so `rankGlKeys` scores every history key against the GL phrase (exact key, else weighted word overlap with short GL words down-weighted and inflections matched by `wordSimilarity`) and `poolRenderings` merges the renderings of all keys. Each pooled rendering is searched in the verse: contiguous, then in order with gaps (polynomial tightest placement), then a tight out-of-order window, then the rendering words the verse contains. If no candidate has a confidence of `FUZZY_PASS_BELOW_CONFIDENCE` (50) or more, an order-aware fuzzy pass matches inflected or compound forms with `wordSimilarity`. Each candidate has a match score (`scoreAlgorithmicMatch`, capped per rendering by `capForRendering`), which only chooses between candidates for the same words and breaks ties (`plans/algorithm-partial-match.md` holds its rationale). The reported confidence, which also orders the options, is `scoreSuggestionFromHistory`: closeness to the history rendering (verbatim 1, lower for gaps, swapped or missing words and fuzzy forms) x GL-key weight (1 for the exact key, 0.36-0.6 for related keys) x verse checks (the words occur more than once in the verse, a word of an exact-key rendering is next to them, another history rendering is in the verse verbatim), with the weights in `HISTORY_SCORE` fitted on the training data (`plans/algorithm-confidence.md`). How often a rendering was chosen does not raise the confidence (on the training data it did not predict the right answer); it only gates 100, which needs a verbatim exact-key match that passes every verse check and was chosen at least `CERTAIN_MIN_HISTORY_COUNT` (5) times, and is right about 95% of the time. `getBestTWordSelectionWithConfidenceAlgorithm(..., { explain: true })` returns each option's `features`, the evidence behind its confidence. `npm run calibrate:algorithm` measures the confidences against the training data.
- With `llmQueryUrl` → the algorithm runs first, and a job whose top option has confidence 95 or more (`ALGORITHM_CERTAIN_CONFIDENCE`: the 95-99 answers were right more often than the fine-tuned model's, see `plans/algorithm-confidence.md`, Step 6; overridden per job by the `algorithmCertainConfidence` option, which `Container.js` takes from the `algorithmCertainConfidence` checking setting that tc-ui-toolkit's configure AI dialog saves, or the older hand-set `llmAlgorithmCertainConfidence`, with `getAlgorithmCertainConfidenceSetting`) gets that answer marked `algorithmFirst` without asking the AI. The rest go to `getBestTWordSelectionWithConfidenceFromLlm(requests)`, which sends them in one batched query (how many per query comes from the `llmGrouping` setting, default `DEFAULT_SUGGESTION_REQUESTS_PER_CALL` in `Container.js`) to an OpenAI-compatible chat-completions server (default `AI_API_URL`). `queryAiAPI` goes through the Electron main process when translationCore provides `window.AiAPIs` (see `getAiAPIs`), and otherwise calls the server directly over HTTP. The prompt (`buildTranslationOptionsPrompt`) has a fixed system prompt per path, so the server's prompt cache keeps working: `LLM_SINGLE_SYSTEM_PROMPT` for one request per query and `LLM_BATCH_BASE_SYSTEM_PROMPT` plus `LLM_BATCH_SYSTEM_PROMPT` for batches. They differ on purpose (rule 3 and the inflected-form example), because each wording was measured on both paths; change them only with measurements (see the plan). `queryAiAPI` puts `/no_think` at the start of the system prompt and of the user message when thinking is off (`applyThinkingDirective`; through `window.AiAPIs` too, since 2026-11-22: before, translationCore sent the user message without it, unlike the fine-tuning data); at the end of the system prompt it made small models drop the batch markers. The history lines (`formatPreviousTranslations`) are every rendering of the group, ranked with `rankGlKeys`, ordered by whether the rendering is in the verse (exactly, or as another form by `wordSimilarity`), then exact key, relatedness and count; at most 10, or 5 when none fits the verse. Response parsing (`parseLlmSelectionOptions`, `extractLlmRows`) is defensive: it handles thinking/reasoning tags, JSON or CSV rows, and missing formatting; a batched answer without `### REQUEST n` markers is split by line only when it has exactly one row per request. Answer words are matched to verse words exactly, then ignoring accents, then by `wordSimilarity`; more than half the words must be found, a match by similarity caps the confidence at `FUZZY_TARGET_MAX_CONFIDENCE` (90), and rows with confidence 0 are dropped. When a job has no history, `getBestSelections` caps the AI's confidences at `LLM_NO_HISTORY_MAX_CONFIDENCE` (70) with `capConfidenceWithoutHistory`: without history AI answers were right far less often than their confidence said, and the UI applies any suggestion with a confidence. The default temperature is 0.1 (`LLM_DEFAULT_TEMPERATURE`), and a setting of 0 is used as given. The optional `llmExtraParams` setting (a JSON object in the checking settings file, with no UI) adds fields to the request body, such as `seed` or `top_k`. They are merged as translationCore's main process merges `extraParams` (`getExtraParams`): they can override temperature, max_tokens and chat_template_kwargs, but not model, stream or messages. The eval suite takes them from `LLM_EVAL_EXTRA_PARAMS`. `LlmRequestQueue` also runs the algorithm path for each AI result (not for `algorithmFirst` ones) and merges its options in with `mergeBestSelections` (one copy of an option both give, with the higher confidence; sorted best first, not cut to 3); `doQuery` marks every algorithm option `isAlgorithmSuggestion`. If the AI gives no suggestion, the algorithm's are used alone and the result is marked `algorithmFallback`. `translatePhraseWithConfidence` is an older single-phrase AI path.

Both paths return up to 3 `{ selections: [{text, occurrence}], confidence }`, best first, so they are interchangeable. Keep that contract when changing either one. Both place a rendering at its first match in the verse; `getBestSelections` then moves each option to the check's `contextId.occurrence` with `moveSelectionsToOccurrence` when the words occur that many times as separate runs (a heuristic: the nth original word is taken to be rendered by the nth run).

Previous-selection history comes from `fetchPreviousSelectionData(...)`. In the same scan `Container.js` (`loadSelectionHistory`) also counts it by the check's original-language quote through the `onBookChecks` hook (`countOlSelections` in `originalLanguageUtils.js`: lemma and surface-form keys from the newest unfoldingWord `ugnt`/`uhb`), including books whose GL bible is missing; each request's `selectionsData.olHistory` (`getOlHistoryForCheck`) goes to the algorithm as its `olHistory` option (weights `OL_KEY_SCORE`), not to the AI (`plans/original-language-history.md`, Steps 2-4). It scans the other projects in the tCore projects folder and returns `{ normalizedGlQuote: { selectedTargetText: count } }`, e.g. `{ 'faith': { 'fe': 12, 'la fe': 3 } }`. Both the gateway-language phrase keys (with the GL code) and the target-language keys (with the target code) are lowercased with `getSelectionHistoryKey` (`toLowerCaseForLang`) when the history is read, when the user saves a selection (`updatedPreviousSelectionsData`) and in alignment history entries, so 'Faith' and 'faith', or 'Fe' at the start of a verse and 'fe', count as one; matching GL phrases to keys (`rankGlKeys`) and renderings to the verse ignores case. The training data builders call `getSelectionsForBook` without the target language, so their histories keep the original case.

Word alignments can add to that history (`plans/alignment-history.md`; off unless the `llmUseAlignmentHistory` setting is on: the "Use word alignments" checkbox in tc-ui-toolkit's Configure AI dialog; changing it clears the cached AI suggestions). `src/utils/alignmentHistoryUtils.js` reads a project's alignments (`getVerseAlignments`, `getAlignedTargetWords`, also used by the training data builders). `fetchAlignmentHistoryEntries` gathers the aligned target words of a group's checks from every project with the same target language and resource id (all testaments), and `getSuggestionHistory` adds them to the selection history for one check. It leaves out the check's own verse in the current project, since that alignment is the answer, and checks whose saved selection the selection history already counts. `Container.js` reads the entries once per group and sends each request its merged history.

Suggestion cache: results are cached in `LlmRequestQueue` by the keys from `generateKey` in `Container.js` (`{toolName}_{glCode}_{targetLangId}_{groupId}_{bookId}_{chapter}_{verse}_{checkId}`; `generateGroupKeyPrefix` builds the part shared by a group). When the user saves a selection, `updateSelectionsData` updates the history in place with `updatedPreviousSelectionsData` and, if suggestions are enabled, clears that group's cached suggestions with `clearSuggestionsMemoryForKeyPrefix`; with AI suggestions on it also regenerates the group right away.

Target languages can be any language, including ones with no linguistic resources: compound or inflected words, any script, any word order. Don't add matching logic that assumes English-like or Latin-script target text, or that needs target-language word lists.

Lowercase language text with `toLowerCaseForLang(text, langId)` (or `normalizeForCompare(word, langId)`), not `toLocaleLowerCase`. Only Turkish, Azerbaijani and Lithuanian lowercase differently from `toLowerCase`, so the helper uses the locale only for those. `toLocaleLowerCase` throws for `''`, follows the computer's language when the code is missing, and is 80-450x slower for codes like `es-419`, `el-x-koine` or `hbo`.

`GitApi.js`, `GogsApiHelpers.js`, `Repo.js`, `ProjectAPI.js`, `ResourceAPI.js` deal with git/DCS (Door43 Content Service) interactions for project/resource management, largely wrapping `simple-git` and `gogs-client`.

### Redux

Actions/reducers follow standard redux-thunk conventions under `src/state/actions/` and `src/state/reducers/`. Selectors (`src/selectors/index.js`) are the intended read path — they wrap both this package's own `state.tool.*` slices and the host `tc` prop, so prefer adding a selector over reaching into state shape directly in components.

### Localization

Component/container strings are translated via `react-localize-redux` (`translate` prop, `getTranslateState` selector); locale files are supplied by the consuming tool (see `localeDir` in the README's usage snippet), not stored in this repo.

## Code style notes (from `.eslintrc`)

- Single quotes, 2-space indent, semicolons required, trailing commas on multiline.
- `no-unused-vars`, `no-undef`, `require-await`, `no-return-await`, and `array-callback-return` are errors, not just style — CI lint will fail on these.
- `react/prop-types` is enforced for components.

## Dependency Modules from unfoldingWord

These are `peerDependencies`: translationCore supplies them at runtime. `devDependencies` pins the versions used for local tests. When behavior depends on one of them (e.g. how `normalizer` handles punctuation or accents), read the installed code in `node_modules/<pkg>`, which matches the pinned version. Don't assume the GitHub default branch matches.

These modules are under our control and may need to be modified as well to implement features or fix bugs.
