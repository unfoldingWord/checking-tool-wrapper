⏺ I wrote the new plan at plans/prompt-span-experiments.md. No code was changed
  and nothing was committed.

  Starting point. plans/improve-single-prompt.md already tested about 20
  wording, data and no-history variants, and none of the prompt changes was
  adopted. Repeating that work would waste runs, so I looked at where the models
  actually fail first.

  What the saved results show for the released 1.7B (scored on the TEST set, as
  the app shows answers):
  - Answer span is the main problem. 182 of its 272 wrong answers have the right
    words but too few or too many. The biggest group is 136 answers that are
    missing a word, usually the target word for a small gateway word in a
    multi-word phrase. For example, for "for Christ" it answered খ্রীষ্টের where
    the expected answer is খ্রীষ্টের জন্য.
  - Rule 2 of the current prompt says "Choose the fewest words." That points the
    model toward exactly this error.
  - 40 of those 136 answers copy a history rendering whole when that rendering
    was chosen for only part of the phrase (the line says "Christ" while the
    phrase is "for Christ").
  - The fine-tunes almost never answer with words that aren't in the verse. That
    rules out output constraints and a "don't answer in the gateway language"
    guard for them.

  The experiments:
  - C1: reword rule 2 to "translate all of the phrase, including small words,
    and no other words."
  - C2: C1 plus a worked example with a multi-word phrase.
  - C3: mark history lines that were chosen for only part of the phrase.
  - C4: the best of C1/C2 combined with C3.
  - C0: rule 2 deleted, only to separate the effect of removing it from the new
    wording.

  Setup choices:
  - Models and server: the three files in ~/translationCore/models, which are
    the released D3 fine-tunes plus the publisher's 4B Q4_K_M, not R0. They run
    on translationCore's own bundled llama-server (build 12651) with the same
    arguments the app uses. The Homebrew build the old plan used is no longer
    installed.
  - A new dev set for screening: the 629 cases of D3's validation split. None of
    them is in D3's or R0's training data, so the fine-tunes can be screened
    fairly without touching TEST.
  - The hypothesis has to hold on the new set first. It came from TEST, which
    has been used many times, so Step 2 stops the work if the pattern doesn't
    show up on the dev set. TEST is used once more at the end.
  - Retraining only if needed. At most two retrains, and only if the
    history-line marking (C3) needs one to work.

  Three questions for you (section 7 of the plan):
  1. Is R0 replacing D3 in the release? The plan assumes D3 because that's
     what's in your models folder.
  2. Should a translationWords selection include the word for a small gateway 
     word? For "for Christ", should translators select খ্রীষ্টের জন্য or only
     খ্রীষ্টের? The expected answers come from word alignments and include it. If
     the checking guidance says otherwise, this whole line of work would make
     real selections worse even while scoring better.
  3. Is a budget of two retrains (about 3.5 hours each) acceptable?
