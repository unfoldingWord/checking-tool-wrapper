  S4 fails the rule for two reasons:
  - The 1.7B's gain on DEV isn't significant.
  - The 4B is significantly worse on DEV: 51.7 → 49.4%, p 0.002.

  S4 still has the most going for it of the six:
  - Fewer confident wrong answers on every model. On DEV, 1.7B 492 → 278, 0.6B
    343 → 6, 4B 529 → 437. This matters because the UI applies any suggestion
    that has a confidence.
  - 0.6B gains on DEV. 39.5 → 41.5%, p 0.004.
  - The 1.7B is faster. Median time drops from 165 to 128 ms.

  Part of that drop comes from lower confidences overall: the 1.7B's mean
  confidence on right answers falls from 86 to 80. It seems to copy the lower
  confidences in the examples.

  Where S4 loses cases:
  - Requests with no possible answers listed: mostly answers of "",0. That's 14
    of 15 lost cases for the 1.7B and 22 of 26 for the 4B.
  - Requests that list possible answers: the 1.7B gains (25 cases won, 12 lost),
    but the 4B loses (28 won, 51 lost).

  S1 doesn't help the stock models. llama-server caches the system prompt, so
  the shorter prompt isn't faster. It stays a retrain candidate only to test
  whether a fine-tune needs the long prompt.

  My recommendation is to take S4, and S1 if you still want the speed test, into
  the Step 7 retrains. They would be retrain candidates, not changes to the
  prompt that ships. A fine-tune learns the format from its training data, so
  the 4B's drop on the stock model matters less there. Before an S4 retrain, I
  need to check how mlx-lm masks multi-turn examples, so training only learns
  from the last answer.

  Two other options:
  - Try S4 with the separate no-history prompt (N3). That would target S4's
    empty answers on requests without possible answers.
  - Run Step 6 next.

❯ are there any changes to the prompt itself that may improve the results for   
  a qwen3 model                                                                 

  Ran 1 shell command (ctrl+o to expand)

⏺ Yes. A few changes look worth measuring, but none has been tested yet, so
  treat these as ideas. Each one targets a failure we saw in the results.

  1. Let the server limit answers to verse words. llama-server accepts a grammar
  field with each request, and we can build one per request that only allows
  quoted runs of TARGET VERSE words. The 1.7B's most common mistake is copying a
  previous translation that isn't in the verse, and the rule against it isn't
  followed: with X1, it still copied a rendering 223 times out of 422 when none
  was in the verse. A grammar makes that impossible.
  - plans/improve-llm-suggestions.md (D1) rejected grammars because answers
    never failed to parse. This is a different use, about content rather than
    format.
  - Cost: per-request code (the fixed llmExtraParams can't carry it), and only
    llama.cpp-based servers support it.
  - Test: an X4b + grammar variant on DEV.

  2. Base confidence on the model's token probabilities. The model's stated
  confidence barely tells right answers from wrong ones. With X4b, the 1.7B's
  mean confidence is 86 on right answers and 83 on wrong ones. That leaves 492
  confident wrong answers, and the app shows any suggestion that has a
  confidence.
  - llama-server can return the probability of each output token (n_probs). The
    probability of the answer's first token usually separates right from wrong
    much better than a stated number.
  - The prompt could then stop asking for a confidence at all. That would also
    remove the examples' confidences, which S4 suggested the model copies.
  - Test: rescore saved answers offline first. That would show whether it helps
    before any new runs.

  3. Have the model choose among the possible answers by letter. X4b already
  lists the algorithm's candidates, and the 1.7B picks the first one about 92%
  of the time. Labeling them A/B/C with a "D: other verse words" option is a
  format small models handle well. It would also give a cleaner probability for
  idea 2.
  - Risk: it could tie the model even more closely to the algorithm.

  4. Use Qwen3's recommended sampling settings. For non-thinking mode, Qwen
  recommends temperature 0.7, top_p 0.8 and top_k 20. We use 0.1, the app's
  default, and these other settings weren't tested here.
  - Test: scripts/test-llm-temperatures.sh plus LLM_EVAL_EXTRA_PARAMS for top_p
    and top_k. It's cheap.
  - Caution: an earlier temperature sweep is why 0.1 is the default, so the gain
    may be small.

  5. Measure thinking mode on a small budget. Thinking is always off
  (/no_think). For a 1.7B, thinking often helps on matching tasks like this one,
  at a large cost in speed.
  - Test: one run with a capped max_tokens would show whether a smaller thinking
    model can beat the 4B. If not, it can be ruled out.

  Not worth repeating: rewording the rules (S1, S2, S5, S6), extra examples
  (N2), or merging the system prompt into the user message (S3). All made the
  1.7B worse or no better.

  The goal is a better fine-tune, and a fine-tune learns the format and rules
  from its training data. Ideas 1 and 2 work outside the prompt, so they would
  help the fine-tunes as well as the stock models. I'd test those two first,
  starting with 2 because it needs no new model runs.

⏺ X4b adds the algorithm's candidate answers to the request. Before asking the
  AI, the app already runs its own matching algorithm. When that finds
  candidates, X4b lists them in a POSSIBLE ANSWERS block, best first:

  PREVIOUS TRANSLATIONS:
  "vương quốc của Thiên Chúa" (chosen 16 times for "kingdom of God")
  ...

  POSSIBLE ANSWERS:
  "vương quốc của Thiên Chúa"
  "vương quốc"

  GATEWAY PHRASE (en): kingdom of God

  Those requests also get a slightly changed system prompt:
  - it explains the block ("may be missing, and may be wrong");
  - it adds one rule: "POSSIBLE ANSWERS are often right: check them first, but
    answer with other verse words when none of them means GATEWAY PHRASE";
  - the first example shows the block.

  When the algorithm finds nothing (always the case with no history), the
  request is exactly the app's current prompt. The "b" marks that difference
  from X4, which used the changed system prompt for every request and hurt the
  4B on no-history requests.
