⏺ Q6 asks how much the app should trust the algorithm before it asks the AI.

  For each check, the app runs its word-matching algorithm first. If the
  algorithm's best answer has confidence at or above a cutoff,
  ALGORITHM_CERTAIN_CONFIDENCE, the app uses that answer and doesn't ask the AI.
  Below the cutoff, it asks the AI, and falls back to the algorithm if the AI
  gives nothing.

  - Cutoff 100 (today's default): the algorithm answers only when it's certain
    (the exact GL key, found word for word in the verse). The AI handles
    everything else.
  - A lower cutoff, such as 60: the algorithm also answers when it's only fairly
    sure, and the AI is asked less often. That helps only when the AI is worse
    than the algorithm on those middling cases.

  Q6 asked whether different models need different cutoffs, since a weak model
  is better asked less. Part of it is already done: the optional
  llmAlgorithmCertainConfidence checking setting overrides the cutoff, with no
  UI and a default of 100. What was left open was the default for each model.

  What testing showed: top-1 on the 835 held-out cases at each cutoff:

⏺ What llmGrouping is: a checking setting that controls how many checks
  translationCore sends to the AI in one request.
  - At 1 (the default): one check per request.
    DEFAULT_SUGGESTION_REQUESTS_PER_CALL = 1 in src/Container.js:95.
  - Above 1: several checks are bundled into one request, and the model has to
    answer each one under a ### REQUEST n marker. With large models, batching
    saves time.

  Why it matters for the fine-tune: the model was trained on single requests
  only. When we tested it with 4 checks per request, it left out the ### REQUEST
  n markers, so translationCore couldn't tell which answer belonged to which
  check. Most answers came back empty: 36% top-1, with 87 empty answers.

  So if someone raises llmGrouping while using this model, their suggestions
  quietly get worse. It isn't a crash. translationCore falls back to its
  matching algorithm when the AI gives nothing, so the user gets the algorithm's
  suggestions without the AI's improvement and without any sign of why.
  Condition 2 under Q4 asks for that to be prevented, or at least flagged.

  Where the guard could go:

  Where: Here (checking-tool-wrapper, Container.js)
  What it would do: Treat llmGrouping as 1 when the model name looks like the
    fine-tune (e.g. contains uw-tw-), and log a warning
  For: Automatic, a few lines, and the same place that reads the setting
  Against: Detecting the model by name is fragile: someone can load it in LM
    Studio under another name
  ────────────────────────────────────────
  Where: translationCore (its settings)
  What it would do: Warn or disable grouping when this model is selected
  For: The user sees the warning when they change the setting
  Against: A change in another repository; same name-detection problem
  ────────────────────────────────────────
  Where: Model card only
  What it would do: Document "use one request per call"
  For: No code
  Against: Relies on people reading it; the failure is silent

  My recommendation: the model card already says this. Add the small guard here
  as well. The default is already 1, so the guard only matters for someone who
  changes the setting, and the fallback means a miss costs quality rather than
  breaking anything. It's cheap insurance.

  I don't know whether translationCore's settings screen shows llmGrouping to
  users. If it does, the warning there would be the most visible option.
